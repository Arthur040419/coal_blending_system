# 煤矿智能配煤管理系统后端需求文档

## 1. 文档目的

本文档用于明确煤矿智能配煤管理系统后端部分的建设目标、功能需求、性能与工程要求、模块边界以及开发范围，为后续基于 Java 的后端项目搭建与开发提供依据。

本系统后端的核心目标是：在已完成数据库建设的基础上，实现基础数据管理、订单管理、规则知识管理、历史案例管理、智能配煤方案生成、方案存储与追溯等功能，并为前端页面和后续智能服务调用提供统一、稳定、可扩展的服务接口。

---

## 2. 系统背景

煤矿智能配煤管理系统面向煤炭配煤业务场景，围绕煤种、煤质、库存、订单、规则知识与历史案例等数据开展统一管理，并在此基础上构建智能配煤决策支持能力。系统后端是业务逻辑处理和数据交互的核心，负责完成数据管理、配煤方案生成、评分排序、结果保存与查询等工作。

根据课题要求，后端不仅要满足常规管理系统的数据增删改查需求，还需要能够支持配煤业务中的约束识别、规则调用、候选方案生成和历史方案追溯等功能，因此其设计应同时体现业务管理能力与智能决策支撑能力。

---

## 3. 建设目标

### 3.1 业务支撑目标

后端系统应支撑以下业务过程：

- 用户登录与基础身份管理
- 煤种、煤质、库存、订单等基础业务数据管理
- 规则知识与历史案例维护
- 根据订单约束生成候选配煤方案
- 对候选方案进行评分、排序和解释
- 保存历史方案并支持追溯查询

### 3.2 工程实现目标

后端系统应满足以下工程要求：

- 接口规范统一
- 模块划分清晰
- 业务逻辑集中管理
- 支持前后端分离开发模式
- 具备一定的可维护性和可扩展性
- 能够满足毕业设计原型系统演示需求

### 3.3 毕设适配目标

后端系统应符合本科毕业设计开发条件，具体包括：

- 采用成熟稳定的 Java 技术栈
- 实现复杂度可控
- 调试过程清晰，便于阶段性推进
- 架构设计清楚，便于论文撰写与答辩展示

---

## 4. 角色需求

当前系统建议支持两类角色：

### 4.1 管理员

管理员主要负责：

- 用户管理
- 煤种、煤质、库存、订单等数据维护
- 规则知识与历史案例维护
- 模型参数配置
- 配煤方案查看与管理

### 4.2 普通业务用户

普通业务用户主要负责：

- 查看煤种、煤质、库存、订单等信息
- 发起智能配煤任务
- 查看方案结果
- 查询历史方案

本科毕设阶段不建议实现复杂的 RBAC 权限模型，可先采用“管理员/普通用户”两级权限控制。

---

## 5. 功能需求

## 5.1 用户与认证模块

后端应支持以下功能：

- 用户登录
- 获取当前用户信息
- 用户列表查询
- 新增用户
- 修改用户
- 启用/禁用用户

说明：前期可采用简化登录方式，后期如有需要可扩展 JWT 鉴权。

---

## 5.2 煤种管理模块

后端应支持以下功能：

- 新增煤种
- 修改煤种
- 删除煤种
- 分页查询煤种
- 按名称或编号查询煤种
- 查询煤种详情

---

## 5.3 煤质管理模块

后端应支持以下功能：

- 新增煤质记录
- 修改煤质记录
- 删除煤质记录
- 分页查询煤质记录
- 按煤种查询煤质记录
- 查询煤种最新煤质指标

---

## 5.4 库存管理模块

后端应支持以下功能：

- 新增库存信息
- 修改库存信息
- 删除库存信息
- 分页查询库存信息
- 按煤种查询库存
- 查询当前可用库存

---

## 5.5 订单管理模块

后端应支持以下功能：

- 新增订单
- 修改订单
- 删除订单
- 分页查询订单
- 查询订单详情
- 更新订单状态

---

## 5.6 规则知识管理模块

后端应支持以下功能：

- 新增规则
- 修改规则
- 删除规则
- 分页查询规则
- 按规则类型查询
- 查询启用状态的规则

---

## 5.7 历史案例管理模块

后端应支持以下功能：

- 新增案例
- 修改案例
- 删除案例
- 分页查询案例
- 查询案例详情
- 按关键词检索案例

---

## 5.8 智能配煤模块

智能配煤模块是后端核心模块，应支持以下功能：

- 根据订单读取配煤约束
- 查询相关煤种、煤质、库存信息
- 检索规则知识与历史案例
- 生成候选配煤方案
- 对候选方案进行评分与排序
- 输出推荐方案和解释信息
- 保存方案及方案明细

说明：该模块前期建议采用“规则筛选 + 计算评分 + 模板化解释”的实现方式，后期再考虑接入 Python 智能服务或大模型接口。

---

## 5.9 方案管理与追溯模块

后端应支持以下功能：

- 查询方案列表
- 查询方案详情
- 查询方案明细
- 按订单查询对应方案
- 选择推荐方案
- 查看历史生成记录

---

## 5.10 系统配置模块

后端应支持以下功能：

- 查询模型配置
- 修改模型配置
- 启用/停用模型配置

该模块在本科毕设中可实现为简化版，主要用于支撑系统完整性。

---

## 6. 核心业务流程需求

### 6.1 基础数据维护流程

系统应支持管理员对煤种、煤质、库存、订单、规则和案例数据进行维护，并保证相关信息可以被智能配煤模块调用。

### 6.2 智能配煤生成流程

系统应支持用户选择订单后，由后端完成以下处理：

1. 读取订单信息
2. 提取配煤约束
3. 查询煤种、煤质与库存数据
4. 检索规则与案例信息
5. 生成候选方案
6. 进行方案评分与排序
7. 输出推荐方案及解释结果
8. 保存方案和明细记录

### 6.3 方案追溯流程

系统应支持用户按订单编号、方案编号或时间范围查询历史配煤方案，并查看方案详情、配比明细、评分结果和解释信息。

---

## 7. 数据需求

系统后端应基于已建数据库完成业务逻辑开发，主要涉及以下核心表：

- `sys_user`
- `coal_type`
- `coal_quality`
- `inventory`
- `orders`
- `rule_knowledge`
- `case_sample`
- `blend_plan`
- `blend_plan_detail`
- `model_config`

后端需要确保各表之间的关联关系被正确使用，并在业务处理中保证数据一致性。

---

## 8. 非功能需求

### 8.1 可维护性

后端采用分层架构设计，避免业务逻辑散落在控制层和数据访问层中，便于后期维护与扩展。

### 8.2 可扩展性

系统后端需预留扩展空间，以支持后续：

- JWT 鉴权
- Redis 缓存
- Python 智能服务接入
- 向量检索服务接入
- 图数据库接入

### 8.3 可测试性

系统后端应具备清晰的接口边界和统一的响应格式，便于通过 Swagger、Apifox 或 Postman 进行测试。

### 8.4 可演示性

后端必须能够支撑完整的系统演示流程，特别是“订单输入—方案生成—历史保存”这一核心主流程。

---

## 9. 接口设计原则

后端接口设计应遵循以下原则：

- 采用 RESTful 风格
- 使用统一返回结构
- 查询接口支持分页
- 新增与修改接口统一使用 `RequestBody`
- 核心业务接口命名清晰，便于前后端联调

建议统一返回格式如下：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

## 10. 开发范围说明

本科毕业设计阶段，后端开发范围建议控制在以下内容：

### 必做内容

- Spring Boot 项目搭建
- 数据库连接与基础配置
- 基础管理模块 CRUD 接口
- 智能配煤主流程实现
- 方案保存与追溯接口
- 接口测试与基础异常处理

### 选做内容

- JWT 登录鉴权
- Redis 缓存
- 操作日志
- 外部 Python 服务调用
- 更复杂的规则引擎

---

## 11. 开发阶段划分

### 第一阶段：项目基础搭建

完成内容：

- 新建 Spring Boot 项目
- 配置数据库连接
- 配置 MyBatis-Plus
- 配置统一返回结构
- 配置异常处理
- 配置接口文档

### 第二阶段：基础 CRUD 模块开发

完成内容：

- 用户模块
- 煤种模块
- 煤质模块
- 库存模块
- 订单模块
- 规则模块
- 案例模块
- 模型配置模块

### 第三阶段：智能配煤模块开发

完成内容：

- 订单约束提取
- 候选煤种筛选
- 规则与案例检索
- 候选方案生成
- 方案评分排序
- 方案解释生成
- 方案保存

### 第四阶段：联调与优化

完成内容：

- 前后端联调
- 接口调试
- 异常处理优化
- 历史方案追溯完善

---

## 12. 验收标准

后端系统完成后，应至少满足以下验收标准：

1. 项目能够正常启动并连接数据库
2. 基础业务模块接口可正常使用
3. 智能配煤主流程可完整运行
4. 配煤方案可保存并查询
5. 接口返回结构统一
6. 能配合前端完成系统演示

---

## 13. 文档结论

通过本需求文档可明确，煤矿智能配煤管理系统后端不仅是普通的数据管理服务，还承担着业务逻辑组织、智能配煤流程控制与方案追溯支撑等重要职责。后续开发应以“先打通主流程，再逐步增强能力”为原则，优先完成基础 CRUD 和智能配煤核心接口，实现一个能够支撑毕业设计展示与论文撰写的后端原型系统。
